Using the Factory

How you'd actually point Atelier at repayd & tmu — before Phase 0

The build plan describes what Atelier will be. This doc is a reality check on what the engine is today and a concrete playbook for the two projects you want to try it on. Short version: both repos are an unusually clean fit — DDD Laravel apps whose domain/ folders map 1:1 onto tests/ folders, already fenced by exactly the deterministic gates SSSF wants (PHPStan, Pest, Rector, phpat boundaries). The engine barely has to bring its own guardrails; the repos ship them.

But you'd be running the SSSF engine as it exists now — not the finished cockpit. Three facts change how you'd use it, and they're in §01.

01 Reality check — what v1 gives you today

Before scoping tasks, internalise where the engine actually is. These aren't blockers — they're the shape of the tool you'd be holding.

Pi only. CC is stubbed.

agent_cc.py raises NotImplementedError. The roster runs entirely through the Pi backend, and validate() rejects any agent set to claude_code before it spawns. The plan's "Opus/Fable via Agent SDK" split is Phase-2+ work. Today: pick Pi-reachable models for every phase.

Commits straight to your branch.

No branch-per-run, no sandbox, no PR, no human-approval phase. A chain that ends in a commit phase does git add -A && git commit on whatever branch you're on. On money-touching repos that's a footgun — you'll add a branch-per-run wrapper (§02).

The test gate is a placebo.

quality.py ships commands that echo and exit 0. Out of the box adw_build_test reports green on a repo with zero real tests run. Wiring your actual verify commands into that one file is the first thing you customise — and it's what makes Atelier trustworthy on these repos.

Net: v1 is observe-first and Pi-driven, exactly as D4 locks it. You run ADWs from the CLI, watch them in the read-only cockpit, and the "launch from UI" / model-stack story arrives in later phases. Plan your first month around that.

02 The onboarding pattern — same six moves for any repo

SSSF installs into a target repo: it stamps an adws/ tree and operates on the git root of the current working directory. There's no "target repo" flag — you cd into the project and run there. So onboarding repayd or tmu is the same recipe:

  1. Stamp the factory. Copy the sssf skill into the repo's .claude/skills/, then uv run .claude/skills/sssf/scripts/install.py from the repo root. This lands adws/, a starter sssf.config.yaml, prompts, and a justfile. Commit it as its own change so it's reviewable and reversible.
  2. Wire quality.py to the repo's real verify commands — the single most important step. Replace the echo placeholders with the actual argv (see per-project §04). This turns the deterministic test/quality gate from theatre into a real acceptance check.
  3. Author the roster in sssf.config.yaml: models per agent (all Pi for now), and — critically — a writes: allowlist per agent scoped to the domain folder you're targeting. The write-boundary enforcer rolls back anything outside it.
  4. Add a branch-per-run wrapper. Since the engine commits to the current branch, front every run with git switch -c atelier/<adw_id>. A three-line shell/just recipe closes the biggest v1 gap for these repos.
  5. Set keys & smoke-test. cp .env.sample .env, add the provider key(s) your models need, then just demo (two cheap read-only runs) and just obs to confirm the trace UI sees the db.
  6. Start read-only. First real runs are adw_scout / adw_plan — no writes, no commits. Read the envelopes and gate evidence in the cockpit before you ever let a builder touch a file.

Why these two repos flatter the engine

SSSF's whole thesis is "agent proposes, deterministic code disposes" — but code can only dispose if the repo has deterministic checks. repayd and tmu both ship: PHPStan/Larastan (repayd at level 8), Pest domain suites organised 1:1 with the domain/ folders, Rector + PHP-CS-Fixer, and repayd even has phpat architecture-boundary tests that fail if a domain imports across its seam. Those are your claim gates. You're not inventing acceptance criteria — you're pointing quality.py at ones that already exist and are already enforced in git hooks.

03 The scoping model — one domain folder per run

Both repos use the same DDD layout: business logic lives in domain/<Module>/, and each module has a matching tests/Domain/<Module>/. That folder pair is your natural unit of work — small enough for one agent to hold, self-contained enough that the write boundary and the test filter line up cleanly.

MoveHow it lands on a Laravel/DDD repo
Scope the writes allowlistwrites: [domain/Forex/, tests/Domain/Forex/] — the agent physically cannot edit outside the module; the enforcer git checkouts any stray file.
Scope the test gateWire the test command as artisan test --filter=Forex (or the folder path) so the gate runs the module's suite, fast, per attempt.
Protect the load-bearing filesprotected_files: already blocks adws/ itself; add database/migrations/, auth, and pivot tables so no agent can touch them without naming them explicitly.
Let phpat/PHPStan be the reviewerArchitecture-boundary + level-8 static analysis catch cross-domain leakage and type errors deterministically — cheaper and stricter than an LLM reviewer for this class of bug.

04 Per-project playbooks

repaydPayments platform · Laravel 12 + Filament · PHPStan L8~36k LOC · 198 test files · high blast radius

Character: regulated fintech — card/bank transactions, payouts, chargebacks, forex, ACI gateway webhooks. Excellent test + lint coverage (your friend), but the money paths are unforgiving. This is a repo where you lean hard on the deterministic gates and keep agents out of the hot zones.

Wire quality.py to

# verify gate  → static analysis + boundaries (fast, no DB)
["composer","phpstan"]         # larastan level 8, respects phpstan-baseline.neon
# test gate    → scoped Pest suite for the module in play
["php","artisan","test","--filter=<Module>"]
# pre-commit style bundle for a fuller pass
["composer","lint"]            # rector + cs-fixer + phpstan + phpmd + phpcpd

Green zone — good first ADWs start here

  • domain/Docs/ — API-doc generation, low risk
  • domain/Forex/ — rate fetch/convert, well-bounded
  • domain/Shared/ helpers, domain/Users/ mgmt
  • Test back-fill on under-covered domains
  • Rector/CS-Fixer cleanup runs (adw_quality)

Red zone — human-only, keep agents out no-go

  • Transactions/, Payouts/ — live money, actively fragile
  • Gateways/ — ACI webhooks, unauth public endpoints
  • Auth: Sanctum, spatie-permission, Breezy 2FA, tenant global scopes
  • database/migrations/ — highest blast radius; some repair live data
  • Deploy: bitbucket-pipelines.yml, s3-*/, docker/

repayd-specific traps

No Co-Authored-By trailers. AGENTS.md explicitly forbids them — override the default commit-message shape in your builder/documenter prompts and the git commit phase.

CI does not run tests. Bitbucket runs only rector/cs-fixer/phpstan/phpcpd; the Pest suite is enforced by local git hooks. So your quality.py test gate is the only automated test signal — it has to be real.

Respect the baselines. phpstan-baseline.neon / phpmd.baseline.xml grandfather existing debt — the gate should fail on new violations only, which the baseline files already handle. Don't let an agent "fix" the baseline.

tmuInsurance admin · Laravel 11 + Filament~13k LOC · 54 test files · moderate coverage

Character: internal back-office — policies, products, distributors, claims, declarations, bulk CSV/Excel import. Smaller and lower-stakes than repayd (no payment gateway; "money" is IPT/premium/percentage math). A single agent holds a whole domain module comfortably. Good repo to build your confidence before letting Atelier near repayd's money paths.

Wire quality.py to

# verify gate
["vendor/bin/phpstan","analyse","--memory-limit=1024M"]
# test gate  (RefreshDatabase → needs the testing DB up)
["php","artisan","test","--parallel","--filter=<Module>"]
# style
["vendor/bin/php-cs-fixer","fix","--dry-run","--diff"]

Green zone — good first ADWs start here

  • Brokers/, Insurers/, Mitigations/, Sections/ — low coupling
  • Reporting/ — additive, read-heavy
  • Test coverage back-fill (only 54 test files → lots of headroom)
  • Fix the stale CLAUDE.md "Vue 3 + Inertia" line — the UI is Filament + Blade

Amber / red — extra care gated

  • Policies/, Products/ — core domains, distributor_percentage splits ripple wide
  • Declarations/ — IPT rate, hosting rate, money-adjacent
  • database/migrations/ — active int→UUID PK conversion; new migrations must not break it
  • Auth: Filament Breezy sessions/2FA
  • Bulk import pipeline (imports, SQS jobs, S3) — failure-prone, external

tmu-specific traps

UUID-as-PK is load-bearing. Observers generate Str::orderedUuid(); the int→UUID migration is mid-flight. Keep agents out of database/migrations/ and don't let them "simplify" the UUID route-key traits.

Tests use RefreshDatabase. The test gate needs the testing Postgres DB reachable (Sail provisions it). If the DB isn't up, the gate fails for the wrong reason — make sure Sail is running before a build+test chain.

CI doesn't run tests here either — same as repayd. Your quality.py gate is the test signal.

06 Cross-cutting guardrails & gotchas

GotchaSevWhat to do
Commits land on your current branchHIGHWrap every write-capable run in git switch -c atelier/<id> first. Never run a build/commit chain directly on develop/master/staging.
quality.py placeholders report false greenHIGHWire real argv before trusting any *_test ADW. This is step 2 of onboarding for a reason.
These are git worktrees w/ symlinked shared configMED.env, CLAUDE.md, AGENTS.md, .claude/ resolve into ../shared/. An agent editing "a config file" may hit shared state across worktrees. Add those symlink targets to protected_files.
CI never runs the test suite (both repos)MEDYour quality.py test gate is the sole automated test signal. Treat a passing gate as the acceptance bar, and still open a PR for human review.
Migrations / auth / money pathsHIGHKeep them in protected_files. repayd payouts+gateways+tenant scopes and tmu's live UUID migration are explicit no-agent zones.
Pi model availability & keysLOWvalidate() only checks model spelling, not keys — a missing provider key fails mid-chain. Point the whole roster at one defaults.model until you need per-phase models, to need one key.

07 Suggested rollout — crawl, walk, run

Sequenced so trust is earned by evidence in the cockpit, not asserted. Maps onto the plan's observe-first v1.

CrawlObserve on tmuread-only, zero commits
  • Stamp SSSF into tmu (smaller, lower-stakes). Wire quality.py. Point cockpit at its sssf.db.
  • Run adw_scout + adw_plan across a couple of green-zone modules. Read every envelope + gate report.
  • Goal: confirm the trace is faithful and the gates fire — no writes yet.
WalkFirst writes on tmu green zonebranch-per-run, test-back-fill
  • Add the branch-per-run wrapper. Run adw_build_test to back-fill tests on Brokers/ / Insurers/.
  • Review the resulting branch as a normal PR. Measure: gate pass-rate, retries, token cost per run in the cockpit.
  • Graduate to a small adw_plan_build_test feature once the loop feels boring.
Runrepayd green zone, gates hardenedmoney paths still human-only
  • Only after tmu is routine. Stamp repayd; wire composer phpstan + scoped Pest + composer lint; enforce no-Co-Authored-By.
  • Scope agents to Docs/, Forex/, Shared/, test back-fill. Transactions/Payouts/Gateways/auth/migrations stay off-limits indefinitely.
  • This is where Atelier's determinism spine earns its keep: level-8 PHPStan + phpat + Pest are a brutal, honest gate. Let them be the reviewer.

Everything above is CLI-launched and watched in the read-only cockpit — i.e. it all fits inside the plan's v1 (Phases 0–1). Launching these runs from the cockpit is Phase 2; none of the rollout waits on it.
